# src/text

Text handling that is common to every byte-level BPE model. Introduced in step 5.

| File | Content |
| --- | --- |
| `bpe.h`, `bpe.c` | byte-level BPE read from `tokenizer.json`: added tokens matched first (leftmost, then longest), NFC, the family's pre-tokenization, merges by rank; decoding to bytes. `ath_spans` (pieces of a text) and `ath_tokens` (a growable list of ids) |
| `unicode.h`, `unicode.c` | UTF-8 decoding and encoding, the character classes pre-tokenization needs (letter, mark, number, white space), canonical combining classes, NFC |
| `unicode_tables.h` | the tables behind `unicode.c`, generated by `tools/dev/gen_unicode.py` and committed; included by `unicode.c` only |

Pre-tokenization (the regex-like split before BPE), the chat template (with tool definitions and the thinking switch) and the output parser (thinking blocks, tool calls) are family-specific: each family provides `pretokenize`, `chat` and `parse` through the contract, implemented as hand-written C in `src/models/<family>/text.c`. No regex engine and no template engine are used.

## Loading

`ath_tokenizer_load` (reached through `ath_model_tokenizer` in the contract) parses `tokenizer.json` into a temporary arena and keeps only the bytes of every token, the added tokens and a hash table of merges (pair of ids → rank and result). The vocabulary is stored in GPT-2's byte-to-character alphabet (a space is "Ġ"); it is mapped back to bytes at load. Anything the engine does not implement is refused with `ATH_ERR_UNSUPPORTED` rather than handled approximately: BPE with an unknown token, byte fallback, dropout, subword affixes or `ignore_merges`; a normalizer other than NFC; a pre-tokenizer other than one Split (Isolated) followed by ByteLevel; added tokens that strip spaces or are normalized. The loader also checks that the file's split regex is exactly the one the family implements (`pretokenize_regex`).

## Unicode versions

The classes come from Unicode 16.0 (Python 3.14's `unicodedata`), the version the reference's regex engine (Oniguruma) uses. NFC does not: Hugging Face tokenizers normalizes with Unicode 9.0 data, so `gen_unicode.py` keeps only the combining classes, decompositions and compositions the reference applies, found by running its NFC and NFD on every entry (21 compositions and 29 combining classes of characters added since 9.0 are left out). Regenerate with the golden environment, which pins both versions:

```
tests/golden/.venv/bin/python -I tools/dev/gen_unicode.py > src/text/unicode_tables.h
```

## Test

`tests/test_text.c`: UTF-8, classes and NFC by hand; against the reference tokenizer (`tests/golden/text.py`), the same ids and the same decoded text for 28 million tokens: texts in many languages, emoji, code, white space, contractions, added tokens in text, files of the repository, every Unicode code point in five contexts and every canonical decomposition with shuffled marks.
